# AI usage telemetry

`programs.aiUsage` acquires usage and quota numbers from AI providers and emits
a **bar-agnostic JSON document**. Bars do not talk to providers. They translate
that document into their own protocol through a small adapter.

This split exists because the original implementation fused five concerns into
one `writeShellApplication` living inside a bar module. That single script did
HTTP, credentials, thresholds, text layout and the bar's `{icon, state, text}`
wire format. Adding a provider meant editing a bar module, and adding a bar meant
duplicating the acquisition logic.

## Architecture

```
                    programs.aiUsage              (policy + acquisition)
                            |
                     lib/default.nix              pure: providers -> config JSON
                            |
                 ai-usage-config.json             version 1, in the Nix store
                            |
        module/package.nix -> ai-usage            fetch, cache, orchestrate
                            |
                  module/ai-usage.jq              pure: body -> document
                            |
                bar-agnostic document             version 1, on stdout
                            |
        +-------------------+-------------------+
        |                                        |
  a bar adapter                        (waybar, polybar, ...)
        |                                          not implemented
  bar-native wire format
```

There are four artefacts with deliberately different purity levels:

| Artefact | May read | Why |
| --- | --- | --- |
| `lib/default.nix` | `lib` only | pure data transformation, unit-testable without a host |
| `module/ai-usage.jq` | its four jq arguments | a pure function, so every semantic rule is testable against a fixture |
| `module/package.nix` | its `callPackage` arguments | an ordinary derivation, and the config arrives as a *file path*, so the package never sees `config` |
| `module/default.nix` | `config.*` | the only file allowed to, and it wires the three above together |

That layering is what keeps everything except `module/default.nix` consumable
outside Home Manager, and it is why this repository can be tested without a host
configuration at all. The rule is a hard one. None of the first three may mention
`config`, `osConfig` or `home-manager`.

Bar translation is deliberately **out of scope** here. A consumer converts the
document to its bar's wire format in its own adapter. This repository ships no
adapter and knows nothing about any bar.

## Config schema (version 1)

The config document is generated by `lib/`, written to the store by the Home
Manager module, and read by `ai-usage`. Disabled providers are **absent** rather
than present with `enable = false`, so querying one is a usage error rather than a
silent empty result.

```json
{
  "version": 1,
  "providers": {
    "<name>": {
      "name": "<name>",
      "enable": true,
      "timeout": 3,
      "refreshInterval": 300,
      "retryInterval": 60,
      "maxStaleAge": 900,
      "source": { "http": { "url": "...", "headers": { "...": "..." } } },
      "credential": { "secretTool": { "service": "...", "account": "..." } },
      "metrics": { "<metric>": { "from": {...}, "unit": "...", "required": true, "nullText": "...", "floor": false } },
      "rules": [ { "metric": "<metric>", "warnAt": 80, "criticalAt": 90 } ],
      "format": "{metric}",
      "tooltipFormat": "{metric}"
    }
  }
}
```

`source`, `credential` and `metrics.<name>.from` are **tagged unions**
(`lib.types.attrTag`), so `{path = ...; expression = ...;}` is unrepresentable
rather than merely undefined.

Several keys are omitted rather than written as null. `credential`,
`tooltipFormat` and `nullText` are omitted entirely when null. `required` is
omitted for `percentOf` metrics, which are never required. `floor` is omitted when
true, so an absent `floor` means "truncate". Only the opt-out is written down,
which is why adding the flag moved no golden file.

Attribute keys are emitted lexicographically by `builtins.toJSON`, which is what
fixes the rendering order of `metrics` in the document.

### `source`

| Tag | Fields | Behaviour |
| --- | --- | --- |
| `http` | `url`, `headers` (attrs of string) | `curl --silent --show-error --fail --max-time <timeout>`. The literal token `{credential}` in any header value is replaced at runtime, so the secret never enters the Nix store. |
| `command` | shell string | stdout is the response body. For providers that expose no usage endpoint at all. |

### `credential`

| Tag | Fields | Behaviour |
| --- | --- | --- |
| `file` | `path`, `jqPath` (default `.`) | reads a JSON file, selects with jq |
| `secretTool` | `service`, `account` | `secret-tool lookup service <s> account <a>` |
| `command` | shell string | stdout is the credential |

An unreadable file, a locked keyring or an empty result all count as a *fetch*
failure. An actionable line goes to stderr and the document degrades, but the exit
code stays `0`.

### `metrics.<name>.from`

| Tag | Fields | Pass |
| --- | --- | --- |
| `path` | list of strings | 1 |
| `timestamp` | `path`, an ISO-8601 UTC instant | 1 |
| `expression` | jq filter over the raw body | 1 (pre-evaluated by the orchestrator) |
| `percentOf` | `of`, `total` | 2 |

The tags are mutually exclusive by *type*, because `metrics.<name>.from` is a
`types.attrTag`. Writing `{path = ...; timestamp = ...;}` fails to evaluate rather
than resolving by some undocumented precedence.

`expression` is evaluated by `ai-usage`, not by the core, and handed in as a
pre-computed value. The core therefore stays a pure function of its arguments,
and a malformed filter cannot corrupt the document.

`timestamp` yields **epoch seconds** and should be paired with `unit = "raw"`,
because percent clamping and dollar flooring would both corrupt an instant.
Emitting a number rather than a formatted string keeps time formatting out of this
repository. A consumer that wants to render "resets in 42m" has everything it
needs, and one that wants an absolute clock time can have that too.

The accepted syntax is exactly `%Y-%m-%dT%H:%M:%SZ`, after fractional seconds and
a `+00:00` or `-00:00` offset are normalised away. Anything else parses to `null`,
including a **non-UTC numeric offset**. For instance `2026-08-21T23:10:00-05:00`
yields `null` rather than a shifted epoch, because reinterpreting someone else's
wall clock as an instant produces a plausible-looking wrong answer, and in a
status bar that is worse than a visible gap. The parse is total for every input,
whether it is a string, a number, a container or absent, and `checks/laws` states
that as `timestamp-total`.

### `metrics.<name>.unit`

| Unit | Clamp | Rendering |
| --- | --- | --- |
| `percent` | to `0..100` | bare number |
| `dollars` | at `0` | `$` prefix |
| `raw` | none | bare value |

`unit` owns clamping and rendering. Truncation to a whole number is a separate
per-metric concern, `metrics.<name>.floor`, which defaults to `true` and is
ignored for `raw`.

### `metrics.<name>.floor`

Truncation is on by default, because a status bar has room for `77%` and not for
`77.9924129335%`, so the document carries the number a bar can show. Set it
`false` when an adapter needs the provider's own precision, for example when
summing currency or drawing a graph. A value of `44.01517413299999` then survives
into `metrics` instead of collapsing to `44`. The flag is per metric rather than
per provider, so one document can carry a truncated `limit` beside a
full-precision `usage`.

There are two consequences, both measured rather than assumed:

- **The rendered form becomes the provider's.** jq reproduces the literal text of
  a number it has not computed on, and Anthropic sends `"utilization": 91.0`, so
  an unfloored percent renders as `91.0%`. A small computed value can appear in
  exponent form, such as `1e-06`. A *computed* whole number renders without a
  `.0` suffix, so `limit - limit_remaining` of `20` still renders as `$20`.
- **A descending rule fires later.** `floor 5.5 <= 5` holds where `5.5 <= 5` does
  not, so with `warnAt = 5` a remaining balance of `5.5` warns when truncated and
  stays quiet when it is not. An ascending rule with whole thresholds is
  unaffected, because `floor v >= T` and `v >= T` agree when `T` is whole.
  `checks/core` pins both halves of that divergence against one fixture, so it is
  a recorded decision rather than a latent surprise.

### `rules`

The document's severity is the **highest** severity any rule yields. No rules
means always `ok`. The alarm *direction* is inferred from the ordering of the
thresholds:

- `warnAt < criticalAt` alarms on high values, comparing with an inclusive `>=`
- `warnAt > criticalAt` alarms on low values, comparing with an inclusive `<=`

`warnAt == criticalAt` leaves the direction undefined and is rejected by a module
assertion.

## Document schema (version 1)

`ai-usage <provider>` prints exactly one JSON object on stdout and always exits
`0`. Bars typically treat a non-zero exit or unparsable output as a hard block
error, so a failed read must still be a valid document. `--raw` is a different
mode with a different contract, described in the CLI section below.

```json
{
  "version": 1,
  "provider": "openrouter",
  "severity": "ok",
  "text": "$7/$20",
  "tooltip": "used $7 of $20 · $12 left",
  "percentage": 37,
  "metrics": { "limit": 20, "percent": 37, "remaining": 12, "usage": 7 },
  "stale": false,
  "age": 0,
  "error": null
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `severity` | `ok` / `warn` / `critical` / `unknown` | worst rule outcome, or `unknown` |
| `text` | string | `format` rendered, or `?` when `unknown` |
| `tooltip` | string | `tooltipFormat` rendered, falling back to `format` |
| `percentage` | number or null | max over `percent`-unit metrics named by a rule |
| `metrics` | object | normalised values in lexicographic order, or `{}` when `unknown` |
| `stale` | bool | serving a cached body after a failed fetch |
| `age` | number or null | seconds since the last good response |
| `error` | string or null | non-null iff `severity == "unknown"` or `stale` |

Invariants, asserted by `checks/core` at named points and by `checks/laws` over a
generated domain:

- `severity == "unknown"` **if and only if** the body is unparsable or some
  required metric resolved to null, and `unknown` implies `text == "?"`,
  `metrics == {}`, `percentage == null` and `error != null`.
- `text` and `tooltip` never contain `<`, `>` or `&`. Bars that render pango
  markup commonly do not escape it, and i3status-rust's `pango-str` formatter is
  one that does not, so those characters would reach pango raw and corrupt the
  block. Stripping happens in the core's `show`, applied to every rendered value.
  That includes `nullText`, which is user-supplied and therefore untrusted. This is
  deliberately *not* a module assertion, because the core must be safe for any
  config, including hand-written ones and the standalone use of `ai-usage.jq`, and
  validation at the module layer would not protect those.
- `text` and `tooltip` contain no residual `{token}`.
- Identical inputs produce byte-identical output. The core reads no clock.

A missing **required** metric makes the whole document `unknown`. That is
deliberate, because a mistyped path should fail loudly rather than render empty
text that looks like a healthy zero.

## Cache schema (version 1)

The cache lives at `$XDG_CACHE_HOME/ai-usage/<provider>.json`. It is written
atomically by writing `<provider>.json.tmp` first and then moving it into place,
and writes are serialised across processes by a `flock` on `<provider>.lock`.

```json
{
  "version": 1,
  "fetchedAt": 1755000000,
  "ok": true,
  "error": null,
  "body": "<raw provider response>",
  "lastGoodAt": 1755000000
}
```

The cache stores the **raw body**, not the rendered document, so changing a
`format` string or a threshold re-renders from cache without a network call.

Refresh policy:

| State | Refetch when |
| --- | --- |
| last fetch succeeded | `now - fetchedAt >= refreshInterval` |
| last fetch failed | `now - fetchedAt >= retryInterval` |
| `--refresh` given | always |

After a failed fetch the last good body is still served, with `stale = true` and
`age` set, until `age > maxStaleAge`. Only then does the document degrade to
`unknown`. A `flock` timeout is not a failure, because the caller falls through to
the cached value.

This is why the bar's poll interval is decoupled from the network. A bar ticking
every 300 seconds against a 300 second `refreshInterval` costs one cache read most
of the time, and lowering the bar interval costs nothing but further cache reads.

## CLI

```
ai-usage <provider> [--refresh] [--raw] [--config <path>]
```

| Exit | Meaning |
| --- | --- |
| `0` | in document mode, a document was printed, possibly an `unknown` one, and this happens always. Under `--raw`, a body was written to stdout |
| `1` | the config file is missing or is not version 1. Under `--raw`, this also covers "no body was available to write" |
| `2` | a usage error, meaning no provider, an unknown provider, a disabled provider, an extra argument or an unknown flag |

`AI_USAGE_CONFIG` overrides the built-in config path, and `--config` overrides
both. Both exist for testing and for running the tool against a scratch config
without a rebuild.

`--refresh` is the only way to force a network call. It is deliberately **not**
bound to a bar click. In i3status-rust, for instance, an explicit click handler
*replaces* the default left-button behaviour, which is format cycling.

### `--raw`

`--raw` prints the upstream response body instead of the document. It exists so a
fixture can be minted without reconstructing the request and its credential by
hand:

```sh
ai-usage claude --raw > checks/core/fixtures/my-capture.json
```

The branch sits *after* cache, lock and staleness resolution and *before*
expression pre-evaluation, so there is exactly one refresh policy in the program.
That means `--refresh`, retry throttling and stale serving all behave identically
in both modes rather than being reimplemented for one of them. A stale body is
still a body, so it is printed with exit `0` while the fetch error goes to stderr.
That is because `stale` and `age` are document-mode concepts and stdout is
reserved for the payload. Output is byte-exact apart from trailing whitespace,
which is normalised to a single newline. Every consumer of a fixture reads it with
`--rawfile` plus `fromjson`, and both tolerate that normalisation.

**The exit-code asymmetry with document mode is deliberate** (D-26). Document mode
implements the status-bar protocol, where waybar, i3blocks and polybar all treat a
non-zero child as a broken module. That is why a failed read is expressed *in the
payload* as `severity: "unknown"` and never as an exit code. `--raw` is an ordinary
Unix filter and obeys ordinary Unix rules, so it **exits `0` if and only if it
wrote a body**. Concretely, `ai-usage claude --raw > fixture.json` must not leave
an empty file behind and report success. There are two modes and two contracts,
each following its own established convention.

`checks/runtime` states the biconditional as a law over every recorded `--raw`
invocation rather than once per scenario. Its limit was found by mutation and is
worth noting. The law sees *protocol* violations and not *correctness* ones.
Reading `.body` straight from the cache file, which bypasses `maxStaleAge`, still
exits `0` with a non-empty stdout and is therefore legal under the law. Only the
value pins catch that mutation.

## Semantics

Let `D` be the parsed body, which is `null` if the body is unparsable. Let `M` be
the metric set and `R` the rules.

Pass 1 performs direct extraction and leaves the value un-normalised:

```
v1(m) = D[path(m)]           if from(m) = path
      = epoch(D[path(m)])    if from(m) = timestamp
      = expressions[m]       if from(m) = expression
      = undefined            if from(m) = percentOf
```

`epoch` is total, which means `epoch(x) = null` for every `x` that is not an
ISO-8601 UTC instant, including a non-UTC numeric offset.

Pass 2 computes the derived metrics:

```
v2(m) = null                             if v1(of) = null or v1(total) = null or v1(total) <= 0
      = v1(of) * 100 / v1(total)         otherwise
```

Pass 3 normalises, and it runs last so that thresholds and percentages are
computed from the *unrounded* values:

```
v(m) = norm(unit(m), floor(m), v1(m) or v2(m))

norm(u, f, x) = null                     if x = null
              = clamp(u, x)              if f = false or u = raw
              = floor(clamp(u, x))       otherwise
```

Severity is then derived from the normalised values:

```
sev(m, r) = unknown   if v(m) = null
          = critical  if (warnAt < criticalAt and v(m) >= criticalAt) or (warnAt > criticalAt and v(m) <= criticalAt)
          = warn      if (warnAt < criticalAt and v(m) >= warnAt)     or (warnAt > criticalAt and v(m) <= warnAt)
          = ok        otherwise

severity  = unknown   if D = null, or any required m has v(m) = null
          = max(sev(m, r) for r in R)   under ok < warn < critical < unknown
```

Multiplying before dividing, as in `of * 100 / total`, preserves precision for
small dollar amounts. Truncating after clamping has two visible effects. A value
of `79.9` becomes `79`, which stays below a `warnAt` of `80`. And `19.6` dollars
against a `20` limit renders as `$19/$20` rather than as a rounded `$20/$20` that
would falsely read as exhausted. Truncation is deliberately the last step and is
skippable per metric, so a `floor = false` metric still gets the clamp its unit
promises.

## Module option reference

`programs.aiUsage`:

| Option | Type | Default | Notes |
| --- | --- | --- | --- |
| `enable` | bool | `false` | installs the `ai-usage` binary into `home.packages` |
| `providers` | attrs of provider | the built-in `claude` and `openrouter` | the registry below |
| `package` | package | built from this configuration | read-only, and consumers should depend on this rather than on a name |
| `configFile` | path | generated | read-only, and holds the store path passed to the binary |
| `settings` | attrs | derived from `providers` | read-only, and described below |

### `settings`

`settings` is the rendered schema-version-1 config document, and it is exactly the
value serialised into `configFile`. It exists so a consumer can assert on *what
this module produced* rather than re-deriving it. A downstream test can read a
single field like this:

```nix
config.home-manager.users.alice.programs.aiUsage.settings.providers.claude.credential.file.path
```

The alternatives are worse. Importing this repository's `lib` from a consumer's
test widens the public API for a test convenience and duplicates the derivation.
Reading `configFile` back with `fromJSON (readFile ...)` is
import-from-derivation inside `nix flake check`. Because `settings` is the single
call site of `mkConfig`, observing it cannot disagree with what was written to
disk.

It is typed `attrs` deliberately. The document's shape is pinned by the golden
diff in `checks/config`, and a second schema encoding as a `submodule` would be a
duplicate owner of the same invariant.

### `providers.<name>`

| Option | Type | Default | Notes |
| --- | --- | --- | --- |
| `enable` | bool | `true` | disabled providers are dropped from the generated config |
| `timeout` | positive int | `3` | the per-request `curl` timeout, so a dead endpoint cannot stall the bar |
| `refreshInterval` | positive int | `300` | minimum seconds between successful fetches |
| `retryInterval` | positive int | `60` | minimum seconds between retries after a failure |
| `maxStaleAge` | positive int | `3 * refreshInterval` | how long the last good body may still be served |
| `source` | tagged union | required | `http` or `command` |
| `credential` | tagged union or null | `null` | `file`, `secretTool` or `command` |
| `metrics` | attrs of metric | required | metric names are the template tokens |
| `rules` | list of rule | `[]` | `{metric, warnAt, criticalAt}` |
| `format` | string | required | `{metric}` tokens |
| `tooltipFormat` | string or null | `null` | falls back to `format` |
| `extras` | attrs of extra | `{}` | optional metric groups, each `extras.<name>.enable` |

An extra contributes metrics and nothing else. It carries no rules, no template
tokens and no intervals. Switching one on takes a single line:

```nix
programs.aiUsage.providers.openrouter.extras.weekly.enable = true;
```

That restriction is what makes non-interference *provable* rather than merely
likely. Because an extra adds no rules, `severity` and `percentage` are fixed.
Because it leaves `format` untouched, `text` and `tooltip` are fixed. Enabling any
combination of extras can therefore only add keys to `metrics`. `checks/laws`
states this over every subset of every shipped provider's extras, and that law is
the whole justification for the restriction.

Extras are a module-layer grouping. `lib/default.nix` merges the enabled ones
into a single flat metric set and never emits the `extras` key, so the config
schema above has no notion of an extra and the pure core cannot behave
differently depending on how a metric got there.

Every shipped extra defaults to `enable = false`, and every metric an extra
contributes is `required = false`. An extra must never be able to render the
whole block `?`.

The module assertions are listed below. Each one names itself in its message and
each has a violating configuration in `checks/module`.

1. every `rules[].metric` names an existing metric
2. `warnAt != criticalAt`
3. `percentOf` operands exist and are not themselves `percentOf`, which is what
   makes the two-pass resolution terminating
4. metric names match `[a-zA-Z][a-zA-Z0-9]*` (they are interpolated into a jq
   regex and used as template tokens)
5. `format` and `tooltipFormat` contain no `<`, `>` or `&`
6. every `{token}` in a template names an existing metric
7. at least one provider is enabled when the feature is on
8. `maxStaleAge >= refreshInterval`
9. a header substituting `{credential}` has a credential source configured
10. no extra defines a metric the provider already defines
11. no two extras of one provider define the same metric

Assertions 1, 3 and 6 quantify over the *effective* metric set, meaning the base
metrics plus the enabled extras, because they constrain the document that will be
emitted. Assertions 4, 10 and 11 quantify over every declared extra whether it is
enabled or not, because they are properties of the declaration. Checking those
only against the enabled subset would mean that a user's `enable = true` is what
breaks the build, leaving them to work out which of the 2^n subsets are legal.
Rejecting the declaration instead puts the error where the mistake is. Assertions
10 and 11 together make the merge order unobservable, because disjoint name sets
mean `//` cannot overwrite anything, and `builtins.toJSON` sorts keys.

## Worked example of an HTTP provider with a keyring credential

```nix
programs.aiUsage.providers.openrouter = {
  source.http = {
    url = "https://openrouter.ai/api/v1/key";
    headers.Authorization = "Bearer {credential}";
  };
  credential.secretTool = {
    service = "openrouter_usage";
    account = "status_bar";
  };
  metrics = {
    usage = { from.path = ["data" "usage"]; unit = "dollars"; };
    limit = { from.path = ["data" "limit"]; unit = "dollars"; required = false; nullText = "∞"; };
    remaining = { from.path = ["data" "limit_remaining"]; unit = "dollars"; required = false; nullText = "∞"; };
    windowUsage = {
      from.expression = ''
        if (.data.limit == null) or (.data.limit_remaining == null)
        then null else .data.limit - .data.limit_remaining end
      '';
      unit = "dollars"; required = false; nullText = "∞";
    };
    percent = { from.percentOf = { of = "windowUsage"; total = "limit"; }; unit = "percent"; };
  };
  rules = [ { metric = "percent"; warnAt = 80; criticalAt = 90; } ];
  format = "{usage}/{limit}";
  tooltipFormat = "used {usage} of {limit} · {remaining} left";
};
```

An unlimited key has `limit == null` and renders as `$7/∞`. In that case `percent`
is null as well, so no rule fires and the severity is `ok`. A zero or absent
`limit` likewise yields no percentage rather than a bogus 100 percent.

It is worth noting which quantity the ratio is taken over. OpenRouter's `usage` is
lifetime spend, while `limit` applies to the period named by `limit_reset`. So
`percentOf(usage, limit)` would compare two different windows and report a
long-lived account as permanently over budget. `limit_remaining` is already
window-scoped server-side, so `limit - limit_remaining` is spend against the
active window whatever the reset period is, and it needs no knowledge of the
`limit_reset` enum. `usage` is kept as informational lifetime spend, and only the
denominator's partner moved. This is legal under assertion 3 because both
`percentOf` operands are pass-1 metrics, with `windowUsage` coming from an
expression and `limit` from a path.

When the server reports a `limit` but no `limit_remaining`, both `windowUsage` and
`percent` are null. The result is no severity signal rather than a plausible wrong
one, which is the same judgement as the non-UTC timestamp rule above.

## Worked example of a command provider

For a service with no usage endpoint, produce the body locally. The provider below
reads a file of spend entries, sums their cost, and compares that total against a
budget carried in the same file:

```nix
programs.aiUsage.providers.local = {
  source.command = "cat ~/.local/state/spend.json";
  metrics = {
    spent = { from.expression = "[.entries[].cost] | add"; unit = "dollars"; };
    budget = { from.path = ["budget"]; unit = "dollars"; };
    percent = { from.percentOf = { of = "spent"; total = "budget"; }; unit = "percent"; };
  };
  rules = [ { metric = "percent"; warnAt = 80; criticalAt = 95; } ];
  format = "{spent}/{budget}";
};
```

A provider of the "credit remaining" kind wants the descending-threshold form
instead. Writing `{metric = "remaining"; warnAt = 5; criticalAt = 1;}` alarms as
the value *falls*, because the warning threshold sits above the critical one.

## Checks

`nix flake check --keep-going` runs five layers, each with exactly one owner:

| Check | Layer | Pins |
| --- | --- | --- |
| `core` | pure core semantics | 46 rows over `module/ai-usage.jq`, covering every semantic rule, thresholds, clamping, truncation and opting out of it, staleness, `percentage`, metric order, pango safety, timestamp parsing and window-scoped ratios |
| `laws` | universally quantified properties of the core | 795 generated instances over a bounded adversarial domain, covering document totality, pango safety, normalisation and its per-metric opt-out, the severity lattice, timestamp totality, determinism and extras non-interference over every subset |
| `config` | pure config builder | the golden `expected.json` for the shipped defaults, plus provider filtering, `percentOf` key omission, null stripping, and drift between the golden and the core's fixtures |
| `runtime` | orchestrator | 58 assertions against stub `curl` and `secret-tool`, covering cold fetch, warm cache with no network, `--refresh`, interval expiry, stale serving, retry throttling, stale expiry, recovery, all three credential kinds, the command source, exit codes, atomic writes, concurrency, and `--raw` over the fresh, throttled, forced-refresh, cold-failure, stale and expired states together with its exit biconditional |
| `module` | Home Manager module | option shape, `settings` contents, package installation, and a violating configuration for each of the eleven assertions |

The golden file `checks/config/expected.json` is the single place the shipped
defaults are pinned. **Consumers must not re-pin them.** A downstream test may
assert on composition, for instance that a user enabled the module, that
`settings` has the providers it expects, or that the credential path tracks
`home.homeDirectory`. Endpoints, thresholds, format strings and units have exactly
one owner, and that owner is here.

`checks/core` pre-evaluates `from.expression` filters itself, mirroring the loop
in `module/package.nix` with the same error handling, because jq has no `eval` and
the core receives expression *values* rather than filters. The duplication is
deliberate, because a shipped filter is only genuinely covered if some check
*executes* it, and no other layer does. `checks/config` pins a filter as text
only, and `checks/runtime` drives its own hand-written config by design. A row may
still declare `expressions` explicitly, which is applied as an override on top of
the resolved values, for a value the orchestrator can produce but a filter cannot.

`checks/module` evaluates the module with `lib.evalModules` against a ~20-line
stub of the three Home Manager options it touches (`home.homeDirectory`,
`home.packages`, `assertions`) rather than taking a `home-manager` input. That
keeps this repository at a single input and keeps evaluation fast.

The cost is **stub drift**: if Home Manager changes the type of one of those
options, this check will not notice. That is acceptable because consumers
evaluate the module inside a real `home-manager` configuration, so drift surfaces
downstream at build time rather than silently.

Assertions are testable in both directions here because in the module system they
are *data* rather than exceptions. They are a list of `{assertion, message}` pairs
that a host evaluator forces later. Forcing the messages only proves that they
evaluate, whereas `checks/module` proves that each one actually fires.

### Laws

`checks/laws` **supplements** `checks/core` and does not replace it. An example row
pins *intent* at a named point, such as the fact that `percentOf(16, 20) == 80`
and the reason why, and it reads as documentation. A law pins *structure* over a
whole domain instead, stating something like `norm . norm = norm`, or that adding
a rule can only raise severity. A green law suite with no examples is unreadable to
the next maintainer, so no example row is ever deleted merely because a law
subsumes it.

The suite is generated in Nix, using `lib.cartesianProduct` over small
boundary-dense domains, and it is verified in jq. There is no property-testing
framework and no randomness. The same instances run on every build, so a failure
is always reproducible from the reported instance. The verifier returns *every*
violation rather than the first, because a harness that reports a single
counterexample is a worse debugger than an example suite.

Some laws need two runs of the core, namely determinism, rule-order permutation,
rule-set inclusion, value monotonicity and normalisation idempotence. Those are
expressed as *paired* instances sharing a `pairId`, which the verifier groups. That
pairing is what lets `f(f(x)) = f(x)` be stated without splitting the core into a
jq module and thereby testing something other than the artefact that ships. The
core is driven exactly as `module/package.nix` drives it, through
`--argjson provider`, `--rawfile body`, `--argjson expressions` and
`--argjson meta`.

Two laws are load-bearing beyond their own statement. **Determinism**, which
states that identical inputs yield byte-identical stdout, mechanically enforces
the purity row of the table above and is the permanent guard against reintroducing
`now` into the core. **`unknown` if and only if the body is unparsable or a
required metric is null** closes the reverse direction that `checks/core` leaves
open, and that is what catches a new optional metric accidentally degrading a
whole provider.

Since jq has no typechecker, the totality laws *are* the type system. The core's
contract is that `(provider, body, expressions, meta) -> Document` is total, and
only a law can state that.

The ceiling is worth stating plainly. Exhaustive laws over a small adversarial
domain are **bounded verification, not proof**, and jq is not verifiable. The
escalation path is the typed-core port listed under extension points. At that
point `proptest` and `kani` bounded model checking become applicable, and this
fixture and law suite transfers unchanged.

## Manual validation

```sh
ai-usage claude | jq .
ai-usage openrouter | jq .

ls -l "${XDG_CACHE_HOME:-$HOME/.cache}/ai-usage/"   # two .json files, no .tmp
```

- Run a provider twice inside `refreshInterval`. The second call must not touch
  the network, which you can see by watching `fetchedAt` in the cache file stay
  put.
- Lock the keyring and then run `ai-usage openrouter --refresh`. The last good
  text is still served with `"stale": true`, and it degrades to `?` only after
  `maxStaleAge`.
- On a host where the module is disabled, `ai-usage` must not be on `PATH`.

Two runtime dependencies are not enforced by Nix, and a missing one degrades the
corresponding provider. The first is a logged-in Claude Code session at
`~/.claude/.credentials.json`. The second is an OpenRouter key in the keyring,
stored with `secret-tool store --label='OpenRouter' service openrouter_usage
account status_bar`.

The Anthropic utilisation endpoint is **undocumented** and may change or disappear
without notice. When it does, the Claude block degrades to `?` and `Warning`
instead of breaking the bar, and `providers.claude.source.http.url` is the override
point.

## Decision register

Code comments in this repository cite design decisions as `D-n`, and this table is
that register. It was written **retroactively**, so read it accordingly. `D-20`
onward are recorded from their own written rationale, while `D-3` through `D-19`
are *reconstructed from their citation sites*, which is the best that can be done
for a decision whose only surviving record is a comment referring to it.

The retroactive reconstruction has two consequences, and both are stated here
rather than hidden:

- `D-1`, `D-2`, `D-7`, `D-8`, `D-9`, `D-12`, `D-14`, `D-15`, `D-16` and `D-18` are
  cited nowhere in the tree, so their meanings are unrecoverable. Do not reuse
  those numbers, because a decision nobody can look up is worse than an unnumbered
  one.
- `D-3` is cited at two sites with two different meanings. In
  `module/default.nix` it means "adding a provider is data rather than code", and
  in `checks/module` it means "evaluate the module against a Home Manager stub
  rather than taking a `home-manager` input". Both are real decisions, and which
  one owns the number cannot be settled now, so both are listed. This collision is
  the reason the register exists.

Entries are deliberately one line each and point at the section that explains
them. The explanation has exactly one owner, and this table is an index rather
than a second copy.

| `D-n` | Decision | Explained under |
| --- | --- | --- |
| `D-3` | Providers are data rather than code, so the built-in `claude` and `openrouter` are ordinary members of `providers` and not special cases | Module option reference |
| `D-3` | *(second citation)* `checks/module` evaluates the module against a 20-line Home Manager stub rather than taking a `home-manager` input, which keeps this flake at one input | Checks |
| `D-4` | `source`, `credential` and `metrics.<name>.from` are `types.attrTag`, so the question "which kind is this?" has exactly one answer instead of an undocumented precedence | Config schema |
| `D-5` | `from.expression` is pre-evaluated by the orchestrator and handed to the core as a *value*, because jq has no `eval` and a malformed filter must not corrupt the document | `metrics.<name>.from` |
| `D-6` | Both `percentOf` operands must be pass-1 metrics, which is what makes the two-pass resolution terminating | Semantics, assertion 3 |
| `D-10` | The alarm direction is inferred from the ordering of `warnAt` and `criticalAt` rather than declared by a separate field | `rules` |
| `D-11` | A null **required** metric makes the whole document `unknown`. `percentOf` metrics are never required, so a required `percentOf` is unrepresentable | Document schema |
| `D-13` | The cache stores the raw body rather than the rendered document, so `refreshInterval` is independent of a bar's poll interval and re-rendering costs no network call | Cache schema |
| `D-17` | A disabled provider is **absent** from the rendered config rather than present with `enable = false`, so querying one is a usage error | Config schema |
| `D-19` | `checks/runtime` drives a hand-written config rather than the output of `lib/`, so the orchestrator stays testable without evaluating the module tree | Checks |
| `D-20` | `from.timestamp` emits **epoch seconds** with `unit = "raw"`, absolute rather than as remaining seconds, because a remaining value is computed at fetch time and is therefore wrong by up to `maxStaleAge` whenever the document is served from cache. Two alternatives were rejected. Injecting `$meta.now` breaks purity and determinism, and a `duration` unit with formatting puts presentation in scope | `metrics.<name>.from` |
| `D-21` | A non-UTC numeric offset parses to `null` rather than to a shifted epoch, because a silent hour-shift is strictly worse than a visible gap | `metrics.<name>.from` |
| `D-22` | `resetsAt` metrics are `required = false` and absent from `format`, because Anthropic returns `null` for an unused window and a null required metric would render the whole block `?` | `providers.<name>`, D-11 |
| `D-23` | OpenRouter's window ratio is `percentOf(limit - limit_remaining, limit)`. `limit_remaining` is already window-scoped server-side, so this needs no knowledge of the `limit_reset` enum and cannot break on an unseen value | Worked example of an HTTP provider |
| `D-24` | Extras are opt-in per group through `extras.<name>.enable` and may add **metrics only**, which means no rules and no template tokens. That restriction is what makes non-interference provable rather than merely likely | `providers.<name>` |
| `D-25` | No API-supplied severity is read, so thresholds remain the single severity engine | Deliberately unused payload fields |
| `D-26` | `--raw` exits `0` if and only if it wrote a body, deliberately breaking document mode's always-`0` contract | CLI, `--raw` |
| `D-27` | Laws are bounded-exhaustive and generated in Nix, with no property-testing framework and no randomness, so every counterexample is reproducible and minimal by construction | Laws |
| `D-28` | Laws drive the core through its real CLI argument interface rather than splitting `ai-usage.jq` into a jq module, so the artefact under test is the artefact that ships | Laws |

The next decision to be recorded is `D-29`.

## Deliberately unused payload fields

Both shipped endpoints return substantially more than this repository reads. The
omissions are decisions, so they are written down. Without this register the next
maintainer re-derives each one from the payload, and "the API offers a severity, so
why are we computing our own?" is a question that deserves an answer in the
repository rather than in a review comment.

The field names below were verified against real captures. The captures themselves
are untracked scratch files, `claude_payload.json` and `openrouter_payload.json`,
because they carry account identifiers and balances. Only the *shape* is recorded
here.

### Anthropic (`/api/oauth/usage`)

| Field | Why it is not read |
| --- | --- |
| `limits[].severity`, `spend.severity` | **D-25.** The API grades its own numbers, but the observed values are only `normal` and `critical`. The middle token is *unobserved*, and guessing it wrong maps silently onto `ok`. Thresholds stay the single severity engine and `rules` is untouched. Permission to break the `rules` schema for this was granted and then declined on YAGNI grounds. |
| `limits[]` with its `kind`, `group`, `percent`, `resets_at`, `is_active` and `scope` fields | A positional array carrying the same utilisation numbers as `five_hour` and `seven_day`, keyed by index. A path into `limits[1]` is a bet on array order that the named keys do not require. `scope` is null for the unscoped entries. |
| `extra_usage.*` | Superseded by `spend`, which encodes the same quantity better. It offers `{amount_minor, currency, exponent}` where `extra_usage` offers `used_credits` plus `decimal_places`. In the capture `extra_usage.utilization` is `null` while `spend.percent` is a number, so the preferred encoding is also the populated one. The `claude.extras.spend` extra reads `spend` and converts minor units inside the extra, so `unit = "dollars"` stays honest. |
| `nimbus_quill`, `tangelo`, `iguana_necktie`, `omelette_promotional`, `cinder_cove`, `amber_ladder`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_cowork`, `seven_day_omelette`, `seven_day_oauth_apps` | Codenamed cohort keys. Every one is `null` in the capture except `nimbus_quill.utilization`, whose sibling `resets_at` is null. An undocumented endpoint's internal codenames are not stable API surface. A metric pointed at one would degrade to `?` the day the cohort is renamed, which is exactly what `required = false` exists to avoid, but there is no reason to carry the metric in the first place. |
| `five_hour.*_dollars`, `seven_day.*_dollars`, `nimbus_quill.*_dollars` | `limit_dollars`, `used_dollars` and `remaining_dollars` are `null` on this account. A dollars view of the subscription windows may appear later, and it would arrive as an extra rather than as a default. |
| `spend.cap` | `spend.cap.money` is byte-for-byte the same money object as `spend.limit`, which the `spend` extra already reads, and `spend.cap.credits` is null. There are two paths to one number, so the extra picks the one whose sibling `used` shares its encoding. |
| `member_dashboard_available`, `spend.disclaimer`, `spend.enabled`, `spend.balance`, `spend.auto_reload`, `extra_usage.is_enabled` | Feature flags, prose and account settings rather than usage. A status bar has no use for them, and `balance` and `auto_reload` are null here anyway. |

### OpenRouter (`/api/v1/key`)

| Field | Why it is not read |
| --- | --- |
| `data.rate_limit` | Declared deprecated by the provider itself, since the object carries `note: "This field is deprecated and safe to ignore."` Reading a field whose own payload says not to would be a liability on the next schema change. |
| `data.label` | The masked API key. It is useless as a metric because it is not a number, and it is semi-sensitive, because extracting it would put it in `metrics` and a `{label}` token would put it on a screen. It is already in the cache file, because the cache holds the raw body. That is an argument for not *promoting* it rather than an argument for scrubbing it. |
| `data.creator_user_id`, `data.expires_at` | Account identity and key lifetime rather than usage. The former draws the same objection as `label`. |
| `data.limit_reset` | Read deliberately by *nothing*, because **D-23** exists precisely to avoid coupling the shipped config to this enum. `limit_remaining` is already scoped to whatever window this names. |
| `data.byok_usage`, `data.byok_usage_daily`, `data.byok_usage_weekly`, `data.byok_usage_monthly` | Bring-your-own-key spend, which is zero on an account that does not use BYOK. It would be additive as an extra alongside `daily`, `weekly` and `monthly` if someone wants it. |

## Planned extension points

Everything below is deliberately **not** implemented. The schema was shaped so
that each is additive.

**OpenAI.** The Costs and Usage API requires an *admin* key rather than a project
key, so it needs a separate credential from the one the CLI uses. `start_time` is
in Unix seconds and `bucket_width` should be `1d`. Results are paginated through
`next_page` and arrive as an array of buckets, so computing a total needs array
aggregation with `from.expression` rather than a path. There is also no spend
*limit* in the response, so a budget has to be supplied by the user. This is
blocked on pagination and on a `literal` metric kind.

**opencode.** Exposes no usage endpoint. The TUI serves per-message cost only, and
it does so on a randomly chosen port, so a `source.command` would have to discover
the port and then walk `/session/:id/message` summing costs. That is possible today
through `source.command`, but it is fragile enough not to ship.

**opencode Zen.** No public balance API at all.

**A `query` value union.** A union of `literal`, `epoch` and `command` for
request-time parameters. It is needed for OpenAI's `start_time`, which must mean
"now minus 30 days" at fetch time rather than at build time.

**A `literal` metric kind.** For user-supplied constants such as a monthly budget,
so that `percentOf` has a denominator when the provider does not give one.

**Pagination.** A `source.http.pagination` field that follows a cursor field until
it is exhausted, concatenating the bodies into an array.

**A systemd warm-cache timer.** This would remove the first-render latency after
login. It is not needed while the bar tick and `refreshInterval` are both 300
seconds.

**Waybar and polybar adapters.** The document already carries `tooltip`,
`percentage` and `stale`, which is more than either bar needs, and only the wire
format differs. Waybar wants `{text, tooltip, class, percentage}`.

**A Rust port of the core.** The jq core is around 120 lines and is fully covered
by `checks/core`. A port would be a performance decision rather than a correctness
one, and the fixture suite transfers unchanged.
